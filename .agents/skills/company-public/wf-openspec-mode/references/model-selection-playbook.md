# 模型选择实战手册 (Model Selection Playbook)

> **适用阶段**: SDD 试行期，手动控制模型选择
> **更新频率**: 月度复盘时更新模型推荐和价格

---

## 1. 双模型策略速查

```
开发者工作流：

  开始任务
    │
    ├─ 需要思考/决策？──→ 用 Tier-1 (Opus)
    │   · 写 spec
    │   · 做架构设计
    │   · 审查实现质量
    │
    ├─ 需要写代码？────→ 用 Tier-2 (Sonnet)
    │   · 按 tasks.md 实现
    │   · 常规 feature 开发
    │
    └─ 简单机械操作？──→ 用 Tier-3 (Flash/Haiku)
        · 补全、格式化
        · 类型定义
        · 归档合并
```

## 2. SDD 四阶段 × 模型映射

| SDD 阶段 | 子步骤 | Tier | 理由 |
|:---|:---|:---|:---|
| **提出** | `/opsx:explore` | Tier-1 | 深度理解代码库需要强推理 |
| **提出** | proposal.md | Tier-1 | 目标对齐是最关键的决策点 |
| **提出** | specs/ (delta) | Tier-1 | 需求完善度决定后续一切 |
| **提出** | design.md | Tier-1 | 技术方案合理性评估 |
| **提出** | tasks.md | Tier-2 | 任务拆解有 spec 约束，相对机械 |
| **执行** | `/opsx:apply` | Tier-2 | 有明确 checklist，不需深度推理 |
| **执行** | 简单 bug fix | Tier-3 | 小范围确定性修改 |
| **校验** | `/opsx:verify` | Tier-1 | 对比 spec vs 实现需要推理 |
| **归档** | `/opsx:archive` | Tier-3 | 机械性文件合并 |

## 3. 特殊升级规则

以下场景**无论当前处于哪个阶段**，一律升级至 Tier-1：

- 涉及支付/收银台核心链路
- 涉及用户数据安全/隐私
- 跨 3 个以上模块的改动
- 性能优化方案设计
- 线上 P0/P1 故障的 hotfix 方案（修代码本身可以 Tier-2，但定位方案必须 Tier-1）

## 5. 试行期数据收集

为后续评估自动路由 ROI，请团队成员在每周五记录：

| 指标 | 收集方式 |
|:---|:---|
| 本周模型切换次数 | 自报 |
| 切换是否顺畅 (1-5) | 自报 |
| 因模型选错导致的返工次数 | 自报 |
| 最频繁的 Tier-1 使用场景 | 自报 |

4 周后用数据决定是否进入 Level 2（半自动分级路由）。
