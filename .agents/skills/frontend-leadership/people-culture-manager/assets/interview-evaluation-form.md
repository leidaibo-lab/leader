## 二、评分规则

评分以目标职级为基准，不按候选人之间的相对表现打分。

| 分数 | 定义 |
| ---: | --- |
| 1 分 | 明显低于目标职级，缺少关键能力或有效证据 |
| 2 分 | 部分达到目标职级，需要较多指导或存在明显风险 |
| 3 分 | 达到目标职级，可以在合理支持下稳定胜任 |
| 4 分 | 明显高于目标职级，在该维度能拉高团队平均水平 |
| 5 分 | 远高于目标职级，并在跨项目或组织层面形成可验证结果 |

评分要求：

- 每项评分必须记录候选人的具体行为、个人责任和结果证据，不能只写“不错”“一般”。
- 面试官先独立评分，再进行集体讨论，避免被第一位发言者影响。
- 总分不能掩盖诚信、责任心、核心岗位能力等关键风险。
- 工作年限、表达活跃程度和技术名词数量不能直接作为职级证据。

## 三、职级总标准

| 职级 | 核心责任 | 达标判断 |
| --- | --- | --- |
| P2 初级 | 生产级交付 | 交付工业级稳定代码，不向 UI 层泄漏脏数据，强类型防御，具备容错机制，无运行时崩溃。 |
| P3-1/2/3 中级 | 领域闭环与重构 | 把控中大型模块状态流转，独立排查内存/渲染问题，具备跨业务线抽象能力。 |
| P4-1/2/3 高级 | 系统杠杆与权威 | 构建防腐层与核心工程体系，Hack 编译底层，解决跨端引擎级难题，对线上崩溃买单。 |
| P5 架构师及前端负责人 | 规则制定与生态 | 定义技术演进战略，强力推行单一事实源，建立高标准自治机制，驱动产研生态升级。 |

> P5 架构师及前端负责人要求具备跨项目技术影响力、机制建设和人才培养能力；同时需承担前端团队或业务线的管理闭环与战略落地。

| 职级 | 达标行为 |
| --- | --- |
| P2 | 严格执行强类型（零 any），无魔法数字，完成网关层数据清洗，实现复杂交互的状态机收敛。 |
| P3-1/2/3 | 精确控制渲染粒度，突破性能瓶颈（FCP/LCP达标），具备跨端/多端底层通信与渲染差异处理能力。 |

| P5 | 掌握技术栈生杀大权，基于 ROI 决定底座革命，强力推行绝对的单一事实源（Single Source of Truth）。 |

## 六、证据核验

围绕候选人的核心项目，按照以下顺序追问：

1. 真实性：具体承担了什么，个人决策和产出是什么？
2. 复杂度：真正困难的约束、规模和协作关系是什么？
3. 决策力：有哪些替代方案，为什么选择当前方案，接受了什么代价？
4. 兜底力：如何监控、降级、回滚、恢复和复盘？
5. 影响力：最终沉淀了什么，多少项目或成员持续使用？

警惕以下信号（红线 Anti-patterns）：

- **黑盒交付/鸵鸟心态**：提测前不自测主流程；看到架构隐患不修复反而继续叠加 `if-else`。
- **魔法代码与失控**：提交未定义的魔法数字、`eslint-disable`，或被问及 AI 生成代码逻辑时答不上来。
- **脱离群众的架构**：搞出极度复杂、业务线无法落地的“空中楼阁”基建，或为了抢进度埋下技术炸弹。
- **屁股决定脑袋**：过度护短，不从整体业务成败出发解决问题，或依靠职级强压不合理方案。

### 录用判断

- [ ] 强烈推荐：达到目标职级，目标岗位核心维度明显高于要求，能够拉高团队平均水平。
- [ ] 推荐：达到目标职级，核心维度无明显短板，风险可在试用期验证。
- [ ] 谨慎推荐：基本达到要求，但必须写清风险、培养成本和验证任务。
- [ ] 不推荐：未达到目标职级，或存在诚信、责任心、核心能力等不可接受风险。
- [ ] 建议调整职级：能力更符合其他职级，需重新对齐岗位需求和候选人意愿。

录用约束：

- 诚信或责任心存在明确问题时，直接不推荐。
- 目标岗位的核心维度低于 3 分时，不能用其他高分抵消。
- 只看加权总分不能形成录用结论，必须结合岗位成功标准和风险判断。
