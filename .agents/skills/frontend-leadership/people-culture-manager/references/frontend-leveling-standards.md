# 前端团队职级要求与定级规则

> 本标准用于统一前端岗位 P2-P5 的职级定义、能力要求和定级边界。
> 职级反映一个人在当前组织中能够持续承担的责任范围和产生的影响，不等同于工作年限、岗位头衔、管理人数或掌握的工具数量。
> 当前阶段不展开面试评价、成长路径、绩效考核和晋升流程；这些方向后续单独讨论，并以本标准为能力基线。

## 一、适用范围与边界

- 适用职级：P2、P3-1、P3-2、P3-3、P4-1、P4-2、P4-3、P5。
- 适用岗位：业务研发、工程平台、技术专家/架构师和前端管理岗位。
- P2 至 P3 以个人稳定交付和模块责任为主；P4 以跨项目系统能力和组织影响为主；P5 以组织级技术战略、机制和业务结果为主。
- P4 及以上允许走技术专家和管理两条通道。两条通道职级价值相当，但责任证据不同，不要求技术专家必须承担人员管理。
- 本标准提供统一基线，不同岗位可以有不同能力重点，但不能降低诚信、质量责任和目标职级的核心责任。
- 本标准只回答“一个职级应能稳定承担什么范围的责任”，不规定具体的人才制度和执行流程。

## 二、定级原则

1. **先看责任，再看技能**：判断实际承担的问题范围、复杂度、自主程度和影响范围，不按技术名词数量定级。
2. **看持续责任，不看单点高光**：定级需要多个相互独立的有效案例或等价持续证据，不因一次高光项目、一次事故处置或短期代理职责上调职级。
3. **结果与过程同时成立**：结果要可验证，过程要体现本人判断、关键动作、风险控制和可复用沉淀。
4. **结合上下文判断复杂度**：同样的结果在不同业务阶段、团队规模、遗留约束和协作复杂度下，证据强度不同。
5. **技术方案服务业务目标**：不把重写、造平台、使用 AST、AI 或某个框架本身当作高职级证据，重点判断必要性、权衡、结果和长期成本。
6. **影响力不等于话语权**：高职级应通过事实、专业判断、机制和协作推动结果，不以强压、信息垄断或个人英雄主义证明能力。
7. **定量指标需要基线**：质量、性能、效率和业务指标应说明统计口径、基线、周期和归因；不设置脱离岗位场景的统一绝对值。

## 三、统一能力模型

| 能力维度 | 核心判断 | 典型证据 |
| --- | --- | --- |
| 业务理解与交付 | 是否理解目标、澄清范围、管理计划与风险，并形成可验收结果 | 需求/方案、里程碑、上线结果、业务或用户指标、复盘 |
| 技术基础与实现 | 是否能选择适当方案，写出正确、清晰、可测试、可维护的代码 | 关键代码、评审记录、测试、性能分析、技术取舍 |
| 架构与工程效能 | 是否能在构建、质量、发布、监控、规范等环节形成可演进能力 | 架构方案、迁移计划、流水线、平台能力、采用与维护数据 |
| 质量、稳定性与安全 | 是否识别风险，设计测试、监控、降级、回滚与安全控制，并承担闭环责任 | 缺陷趋势、告警、演练、故障处置、复盘改进、安全审查 |
| 复杂问题与决策 | 是否能定义问题、识别约束、比较方案、作出取舍并根据反馈调整 | 决策记录、备选方案、排障链路、实验数据、取舍说明 |
| 协作、影响与人才发展 | 是否能建立共识、推动跨角色结果、沉淀知识并帮助他人成长 | 协作反馈、规范/RFC、带教结果、采纳情况、梯队变化 |

AI 是工作方式，不是独立职级维度。各职级都可以使用 AI，但必须能够说明上下文、评审生成内容、补充验证、保护数据，并对最终结果负责。

## 四、职级总览

| 职级 | 角色定位 | 典型责任范围 | 问题模糊度 | 主要影响范围 |
| --- | --- | --- | --- | --- |
| P2 | 成长中的独立贡献者 | 明确任务、小型功能 | 低，目标和方案较明确 | 个人任务 |
| P3-1 | 独立功能开发者 | 完整功能、小型模块 | 中低，能补齐实现细节 | 模块/迭代 |
| P3-2 | 核心模块负责人 | 复杂模块、中型项目 | 中，需主动拆解和权衡 | 项目/小组 |
| P3-3 | 业务领域骨干 | 核心链路、多人项目 | 中高，需处理跨角色约束 | 业务线/多个项目 |
| P4-1 | 系统负责人 | 跨模块系统、关键项目 | 高，需定义方案和边界 | 跨项目/跨团队 |
| P4-2 | 领域专家或平台负责人 | 领域平台、系统性治理 | 高，需平衡长期演进与当期结果 | 多业务线 |
| P4-3 | 组织级技术负责人 | 关键技术领域、复杂项目组合 | 很高，需处理组织级约束 | 前端组织/产研链路 |
| P5 | 架构师或前端负责人 | 技术战略、组织机制、重大业务目标 | 战略级，需定义方向和治理方式 | 公司或事业群 |

子级是责任和影响范围的连续递进，不是“P3-1 只做状态管理、P3-2 只做性能、P3-3 只做基建”这类能力标签。高一级默认应稳定满足低一级的核心要求。

### P3-1 与 P3-2 边界判定

P3-1 和 P3-2 的关键差异不是技术难度，而是责任对象从“完整功能”扩大到“复杂模块或中型项目”。

| 判断维度 | P3-1 | P3-2 |
| --- | --- | --- |
| 核心定位 | 功能负责人 | 模块/项目负责人 |
| 责任对象 | 一个完整功能或小型模块 | 一个复杂模块或中型项目 |
| 目标模糊度 | 目标和总体方案较清晰，能够补齐实现细节 | 目标明确，但方案、拆解和实施路径需要主动定义 |
| 自主程度 | 独立完成执行闭环，重要方案接受上级校准 | 主动形成方案、里程碑、依赖和风险控制，上级主要校准关键决策 |
| 典型跨度 | 单次或少量迭代，通常 2-6 周 | 跨多个迭代，通常 2-4 个月 |
| 协作责任 | 推动本人负责功能的产品、后端和测试协作 | 对多人、多角色共同交付承担协调和结果责任 |
| 技术责任 | 代码、测试、监控和上线质量 | 模块边界、数据流、接口契约、发布回滚和演进成本 |
| 结果证据 | 功能按预期上线并稳定运行 | 项目目标达成，且质量、性能、效率或维护成本有可验证改善 |

判定规则：

- 一个人独立完成了技术难度很高的功能，如果没有承担模块拆解、多人协作、风险控制和整体结果责任，仍属于表现优秀的 P3-1。
- 判定为 P3-2，至少需要两个相互独立的复杂模块或中型项目案例；只有一个案例时应判断为证据不足，不能直接认定已稳定达到 P3-2。
- “协调 2-3 名成员”和时间跨度是常见场景，不是机械门槛；评审仍以实际责任、复杂度、自主性和结果为准。
- 表中的时间跨度只用于理解责任规模，不按在岗年限定级。

## 五、分职级行为锚点

### P2：在指导下完成生产级交付

**核心责任**：在明确目标和合理指导下完成任务，对自己的代码、测试和交付状态负责。

- 业务与交付：理解需求和验收标准，能拆分个人任务、给出进度，并在风险影响交付前主动同步。
- 技术与实现：掌握岗位所需的 JS/TS、CSS、框架和 Git 基础；遵循项目规范，处理常见的加载、空态、异常和权限边界。
- 工程与质量：会使用项目已有的构建、检查、测试、发布和监控工具；提测前完成必要自测，不绕过质量门禁。
- 问题解决：能使用日志、Network、断点和错误堆栈定位常见问题；无法解决时能带着现象、已尝试动作和判断请求帮助。
- 协作与成长：及时反馈进展，接受评审并完成修改；能够解释本人提交以及 AI 辅助生成代码的逻辑和风险。

**有效证据示例**：独立完成若干明确功能；交付记录完整；常见缺陷能够自主定位；评审问题不重复发生。

### P3-1：独立负责完整功能

**核心责任**：在目标清晰的情况下，独立完成从需求澄清、方案、开发、测试到上线观察的功能闭环。

- 业务与交付：主动补齐异常流程和验收边界，能够协调前后端、产品和测试完成联调与上线。
- 技术与实现：合理拆分组件和状态，保持类型、接口和领域边界清晰；能解释常见性能与可维护性取舍。
- 工程与质量：为核心逻辑补充测试和监控，遵循发布与回滚要求，减少可预防的重复缺陷。
- 问题解决：独立定位本模块常见线上问题，完成止损、修复、验证和影响确认。
- 协作与成长：输出必要文档，主动分享上下文；能帮助 P2 解决明确问题。

**有效证据示例**：至少一个完整功能闭环；关键边界有测试或监控；能说明本人决策、结果和改进。

### P3-2：负责复杂模块或中型项目

**核心责任**：面对存在不确定性的复杂模块，能主动拆解目标、形成技术方案并控制交付风险。

- 业务与交付：识别需求冲突、依赖和风险，组织必要评审，推动项目按可验证的里程碑交付。
- 技术与实现：能够设计模块边界、数据流和接口契约；在性能、复杂度、交付速度与演进成本之间作出合理取舍。
- 工程与质量：能完善项目在构建、测试、发布、监控中的薄弱环节，并用数据验证改进效果。
- 问题解决：能处理跨模块故障或性能问题，形成根因分析和预防措施，而不是只修复表象。
- 协作与成长：协调 2-3 名成员完成共同目标；稳定带教 P2/P3-1，并通过评审提升团队交付质量。

**有效证据示例**：复杂模块方案和落地结果；风险被提前识别并处理；质量、性能或效率指标有明确改善。

### P3-3：承担业务领域或核心链路责任

**核心责任**：对一个业务领域、核心链路或多人项目的持续演进负责，推动业务目标、技术质量和协作效率同时改善。

- 业务与交付：理解关键业务指标和领域规则，能将模糊目标转成项目组合、优先级和阶段结果。
- 技术与实现：主导核心模块演进和重要重构，控制兼容、迁移、数据和回滚风险；抽象以真实复用需求为前提。
- 工程与质量：建立领域内可复用的质量、发布和监控实践，持续降低故障、返工或维护成本。
- 问题解决：主导复杂故障或历史问题治理，能穿透前端、网关/BFF 和服务端协作边界定位根因。
- 协作与成长：推动跨角色决策落地；培养可独立负责模块的成员，减少领域对个人的单点依赖。

**有效证据示例**：核心链路持续稳定交付；跨项目改造可控落地；业务或工程指标改善；形成至少一名可接替的模块负责人。

### P4-1：负责跨项目系统和关键技术项目

**核心责任**：定义跨模块系统边界，主导高复杂度技术项目，并为业务连续性和长期可维护性负责。

- 业务与交付：将业务目标、技术约束和资源条件转化为可执行路线，能管理跨团队依赖和重大风险。
- 技术与实现：主导架构设计、演进或迁移，明确备选方案、兼容策略、可观测性和退出机制。
- 工程与质量：建设跨项目复用的工程能力，关注采用率、维护成本和业务收益，不以“平台上线”作为完成标准。
- 问题解决：主导高影响故障处置和复盘，推动系统性改进；能处理跨层、跨端或遗留系统的复杂约束。
- 协作与成长：通过 RFC、评审和共同目标影响多个团队；培养 P3 骨干并完成关键知识转移。

**有效证据示例**：关键系统或迁移项目稳定落地；跨团队采用并产生可量化收益；重大风险得到前置控制。

### P4-2：形成多业务线可复用的领域能力

**核心责任**：在一个重要技术或业务领域形成组织杠杆，使多个团队能以更低成本、更高质量完成工作。

- 业务与交付：能够为领域建立中期路线图，以业务优先级和投入产出决定建设节奏。
- 技术与实现：对领域关键架构有系统判断，能治理一致性与差异化，避免过度统一和重复建设。
- 工程与质量：把构建、测试、发布、监控、安全和规范串成可持续机制，并建立明确的服务等级和维护责任。
- 问题解决：解决多个项目反复出现的共性问题，能验证根因、推广方案并根据使用反馈迭代。
- 协作与成长：建立跨业务线共识和贡献机制；培养多名领域骨干，使能力不依赖本人日常介入。

**有效证据示例**：多业务线持续采用；交付效率、质量或成本改善有基线和趋势；维护、退出和治理机制清晰。

### P4-3：承担组织级关键技术领域责任

**核心责任**：在前端组织或产研链路中承担关键技术领域责任，处理重大不确定性，并影响组织的技术决策方式。

- 业务与交付：参与重大业务和技术规划，识别跨项目资源冲突，推动关键项目组合取得阶段结果。
- 技术与实现：在至少一个关键领域具备公认深度，同时能做跨领域权衡；对重大技术决策的长期结果负责。
- 工程与质量：建立组织级治理机制和度量方式，推动质量、稳定性、安全或效能持续改进。
- 问题解决：处理高风险、长周期、跨组织问题，能在信息不完整时作出可逆决策并控制试错成本。
- 协作与成长：影响业务负责人和产研管理者形成共识；培养 P4 级负责人或专家，建立稳定梯队。

**有效证据示例**：组织级技术决策被多个团队验证；重大项目或治理机制持续运行；关键领域形成继任者和共同维护者。

### P5：定义技术战略并建设组织能力

**核心责任**：把公司或事业群业务目标转化为前端技术战略、组织机制和能力建设，对中长期业务结果与组织健康负责。

**共同要求**：

- 业务与战略：能够与业务和产研负责人共同定义问题，形成 1-3 年方向、阶段目标、资源选择和退出条件。
- 技术与治理：对关键架构、平台和技术投资作出组合决策，建立决策、质量、稳定性、安全和效能治理闭环。
- 组织影响：让多个团队在清晰边界下自主运行，避免依赖个人拍板；能够解释技术投入的业务价值和机会成本。
- 人才与文化：建立负责人和专家梯队，形成公平的授权、反馈、发展和纠偏机制。
- AI 与效率：将 AI 作为产研协作和工程治理能力，关注真实交付结果、质量责任、知识沉淀和规模化边界，不以工具使用率代替组织价值。

**技术专家/架构师通道补充要求**：定义关键技术领域战略，解决行业或公司级复杂问题，形成可持续演进的技术生态，并培养多名领域负责人。

**管理通道补充要求**：对团队目标、资源配置、跨业务线交付、人才梯队和组织健康承担完整责任，能够通过负责人机制放大组织产出。

**有效证据示例**：战略目标被拆解并持续执行；关键技术投资产生业务或组织收益；多个团队形成稳定自治；P4 负责人或专家梯队可持续。

## 六、岗位通道边界

统一职级基线不因岗位通道改变，但不同岗位可以使用不同类型的结果证明同一职级价值：

| 岗位通道 | 主要责任证据 | 共同底线 |
| --- | --- | --- |
| 业务研发 | 复杂业务交付、用户或业务结果、领域演进 | 技术基础、工程规范、质量和协作责任 |
| 工程平台 | 平台采用、工程效率、质量稳定性和维护结果 | 业务价值、长期维护和退出边界 |
| 技术专家/架构师 | 关键领域深度、系统决策、重大问题解决和组织影响 | 业务判断、知识转移和长期成本意识 |
| 前端管理 | 目标交付、资源决策、组织协作和人才梯队 | 技术判断、质量责任和业务价值表达 |

P4 及以上需要形成一个清晰的主通道，但不能用主通道优势完全抵消共同基线中的明显短板。

## 七、证据标准

每条核心证据至少回答以下问题：

1. **背景**：业务目标、约束、规模和当时基线是什么？
2. **责任**：本人承担什么责任，哪些不是本人负责？
3. **判断**：比较过哪些方案，为什么这样选择，接受了什么代价？
4. **行动**：本人完成了哪些关键动作，如何协调他人和控制风险？
5. **结果**：业务、质量、效率、成本或人才结果如何，口径和周期是什么？
6. **持续性**：结果是否持续，是否被复用，离开本人后能否正常运行？

以下内容不能单独证明职级：

- 工作年限、学历、原公司头衔或管理人数。
- 会使用某个框架、构建工具、AI 产品或底层技术名词。
- 代码行数、文档数量、会议次数、加班时长或救火次数。
- 一次高光项目、一次重大故障处置或缺少上下文的百分比指标。
- 只有团队结果，无法说明本人责任、判断和关键贡献。

## 八、定级与校准规则

定级结论只使用三种口径：

- **达到目标职级**：责任范围、复杂度、自主程度和影响范围均达到目标职级，并有持续结果证据。
- **未达到目标职级**：存在明确事实证明核心责任或共同底线未达到要求。
- **证据不足**：缺少足够责任机会、案例归因不清或结果尚未持续，不能根据潜力和印象补全结论。

定级时遵循以下规则：

1. 先判断实际承担的责任范围，再判断六个能力维度，不先计算总分。
2. 高一级默认稳定满足低一级核心要求，不能只凭某个突出技术点跨级。
3. 同一职级允许岗位通道不同，但责任复杂度、自主性和影响范围应保持同等价值。
4. P3 及以上通常需要至少两个相互独立的有效案例；P4 及以上还必须证明跨项目影响和知识转移；P5 必须证明组织级持续结果。
5. 团队结果必须区分本人贡献，个人结果也要说明团队支持和业务上下文。
6. 定级争议应回到事实和证据，由跨团队人员使用同一标准校准，不能由单一直属负责人按印象决定。

## 九、不可补偿红线与偏差防范

以下问题不能依靠其他维度高分直接抵消，但必须基于事实调查和公司制度处理，不能仅凭评价者主观印象：

- 伪造经历、数据、结果或隐瞒重大事实。
- 明知存在重大质量、安全或合规风险仍绕过流程上线，造成严重影响。
- 对事故、延期或风险故意隐瞒、推诿责任，拒绝参与止损和复盘。
- 使用 AI 或外部工具处理敏感数据、引入代码时违反安全与许可要求，且未履行审查责任。
- 通过侮辱、威胁、打压异议、信息垄断或职级压制破坏团队协作。

校准时还应主动防范以下偏差：

- 用工作年限代替能力证据。
- 用口才、可见度、加班和救火频率代替持续贡献。
- 对业务研发和平台研发使用完全相同的结果指标。
- 只奖励新建系统，不认可维护、治理、迁移和降低复杂度的价值。
- 把团队共同结果全部归给负责人，或忽略低职级成员的关键贡献。

## 十、后续专题边界

以下内容当前不在本标准中展开，后续形成独立规则或模板时再与本标准对齐：

- 面试流程、题目设计、评分权重和录用决策。
- 试用期目标、成长梯度、培养路线和导师机制。
- 绩效周期、绩效权重、奖惩和低绩效处理。
- 晋升申报、答辩流程、评审组织和复核周期。
- 职级与薪酬、编制、岗位头衔之间的映射。

后续专题可以定义各自的执行方式，但不能把工作年限、工具清单、单次结果或主观印象重新变成职级标准。
