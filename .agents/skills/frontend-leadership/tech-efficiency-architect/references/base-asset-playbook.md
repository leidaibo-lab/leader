# 基础资产建设与业务推行

## 核心定位

模板项目、组件库、工具库和小程序模板，不是工具清单，而是复用底座。

## 适用资产

- 模版项目优化打磨
- APP 组件库
- Web 组件库
- 工具库
- 小程序项目前置搭建
- 景云销组件 React 重构
- 景云销项目 React 重构

## 演进路径

1. 0 -> 1：先把能用的东西做出来
2. 1 -> 2：打磨稳定性、文档和接入方式
3. 2 -> N：推动业务项目真正使用

## 推广动作

- 先选一个试点项目
- 再补接入清单和迁移说明
- 再统计覆盖率和复用率
- 再做版本化维护

## 公共基建启动与履责

组件库等公共基建不是依赖个人热情的志愿工作。启动前必须同时明确唯一负责人、可投入工时、调度权限、首个交付物和完成期限；缺少任一条件时，先补机制，不直接评价成员主动性。

机制明确后仍未启动时，按以下顺序处理：

1. 基于可观察事实识别阻塞，区分资源冲突、能力不足和承担意愿不足，不公开贴“缺乏主动性”的标签。
2. 资源冲突由上级协调排期；能力不足时缩小首期范围并安排带教，但负责人仍承担推进和风险上浮责任。
3. 约定三个工作日内形成首个可验收结果，例如问题清单、优先级和首个两周计划。
4. 到期仍无结果且未主动反馈风险时，更换负责人，并记录已接受责任、未启动、未反馈和未上浮的履责事实。
5. 重复发生时，调整其骨干、负责人或梯队人选定位；达到组织绩效处理条件后，再进入正式绩效改进流程。

前端负责人负责资源协调、节奏检查和跨团队兜底，不重新把执行工作收回个人手中。否则团队会形成“只要保持沉默，最后仍由负责人完成”的错误预期。

## 评估指标

- 新项目启动时间
- 接入项目数
- 复用率
- 维护成本
- 文档完备度

## 结论

资产建设的判断标准不是“做没做”，而是“有没有真正进入业务交付”。
